# Living World — Product

- **Product:** Living World
- **Purpose:** make Paper/Purpur survival worlds feel alive, reactive, convenient, and capable of evolving over long-running play without replacing the world's primary generator.
- **Primary users:** players and server owners who want a richer survival experience without requiring a client modpack.
- **Current scope version:** Foundation v0.1
- **Requirements authority:** this document + explicit user decisions captured in `TASKLIST.md` / `DESIGN.md`.
- **Protocol:** Agent Development Protocol v2.2 snapshot in this repository.

## Product principles

1. **Living, not noisy.** Changes should be meaningful and often gradual rather than constant spectacle.
2. **Server-side first.** Prefer mechanics that work with normal compatible Minecraft clients.
3. **Composable modules.** Calendar, seasons, climate, world memory, travel, and QoL should have clear ownership and optionality.
4. **Performance is a feature.** Avoid wasteful polling, unbounded scanning, and hidden gameplay compromises.
5. **Worldgen is not our job.** Living World should operate on top of worlds generated by Minecraft or specialized worldgen projects.
6. **Evolution over replacement.** Start with small coherent systems and deepen them only when evidence/gameplay justifies the complexity.
7. **Internationalization from the start.** PT-BR is the canonical/default language, and user-facing text follows a message catalog so new languages do not require code rewrites.

## Planned capability families

These are product directions, not promises that all are implemented in the current scope.

- world time, calendar, months/years, and seasons;
- climate and environmental events;
- desire lines / paths created by repeated player movement;
- small ecological/evolutionary behaviors;
- waystones and travel QoL;
- double doors and other focused convenience mechanics;
- environmental reactions and long-term world memory.

## Calendar direction

- The Living World calendar has 12 months per year.
- Seasons will map to 3 months each in LW-012.
- The initial season order is Primavera → Verão → Outono → Inverno; the cycle is a policy and may evolve without changing persisted calendar history.
- Initial pacing is 8 Minecraft days per month, for 96 days per Living World year.
- Calendar progress is durable logical state; administrative changes to Minecraft time must not rewrite the historical date.
- Month duration is a policy value rather than a hard dependency of the date model, so server pacing can evolve later.

## Climate direction

- A biome/region contributes a base thermal and moisture profile instead of hard-coded gameplay logic being scattered through listeners.
- Seasons apply moderate, predictable influence to that profile.
- Short-lived climate anomalies are bounded so a long-running server cannot drift infinitely hot, cold, wet or stormy.
- The first climate policy outputs a weather tendency rather than immediately modifying blocks, entities or the whole world.
- Concrete Paper weather scheduling and environmental events are a separate integration step (LW-021).
- Representative world climate should use Paper's coordinate temperature/humidity APIs so custom worldgen can participate without requiring hard-coded biome-name compatibility tables.

## Desire Lines direction

- Repeated ordinary walking can gradually convert grass to dirt and dirt to a path.
- Tracking is event-driven and sparse; the feature must never discover traffic by scanning the world.
- Per-chunk traffic memory is bounded and durable through Chunk PDC.
- Teleports do not count as foot traffic.
- Recovery/regrowth is a later evolution step and must reuse tracked state rather than adding whole-world scans.

## Double Doors direction

- A normal manual interaction with one half of an unambiguous matching double door mirrors the final open/closed state to its pair.
- Main-hand filtering prevents duplicate processing from the interaction event firing per hand.
- Iron/redstone-powered doors are not overridden.
- Triple rows or ambiguous neighboring doors are intentionally left untouched.

## Explicitly out of scope

- recreating Terralith, Tectonic, or equivalent heavy world-generation systems;
- building a large custom structure-generation platform;
- requiring Fabric/NeoForge client mods for the base plugin;
- Paper/Fabric hybrid server stacks;
- speculative NMS/packet machinery when public Paper APIs are sufficient;
- hidden balance/gameplay changes justified only as "optimization."

## Foundation v0.1 acceptance

The foundation is accepted when:

- the plugin builds on Java 25 against the selected Paper 26.3 API;
- the main plugin class is a small composition root;
- a minimal module lifecycle exists with deterministic enable/disable behavior and rollback on startup failure;
- user/admin-facing messages have an i18n foundation with deterministic PT-BR fallback and optional additional locales;
- tests cover the module lifecycle and message fallback behavior;
- project documentation, task inventory, roadmap, and checkpoint are recoverable for a new agent.
